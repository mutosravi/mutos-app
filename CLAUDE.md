# Notes for Claude working on this repo

This is the **Muto's app** (repo mutosravi/mutos-app, Worker `mutos-app`, Supabase project "Mutos App" plbixpdyxpayyzpzrvna, later app.mutosstudio.com). It started as a copy of the season team app (mutosravi/mutos-team-app, frozen for the 2026–27 season, restore point branch `season-2026-live`). Build new studio departments here; never push studio features to mutos-team-app.

- The board is a single file, `src/shoot-board.html`, shared with the Claude-hosted artifact (it has no `<html>` wrapper). Never hand-edit `public/board.html`; edit the source and run `python3 tools/build-board.py`.
- App-only behaviour in the board is guarded by `window.MUTOS_APP` (Login Gmail field, `MUTOS_APP.attach(...)` after first load, `MUTOS_APP.changed()` after crew-relevant saves). The board must keep working with no `window.MUTOS_APP` and with the Claude runtime.
- `public/shim.js` implements `window.claude.use('db' | 'user')` on top of Supabase table `docs (collection, id, data jsonb)` with realtime; other capabilities return null.
- `public/crew-sync.js` builds each crew member's page with the board's `crewFeedFor(key)` and upserts `crew_feed`; the owner's board also keeps `members` (role crew) in step with the Login Gmail fields.
- Crew actions: `supabase/002_crew_actions.sql` (crew_away with a trigger that decides auto/pending, crew_status, push_subs). `public/team-updates.js` mirrors accepted crew dates into board `unavailability` with ids `crew-<uuid>` and shows the Team updates window. Reminders: `worker/index.js` (cron in `wrangler.jsonc`, secrets SUPABASE_SECRET_KEY + VAPID_PRIVATE_KEY), `public/sw.js`, `public/push-client.js`.
- Access rules live in `supabase/schema.sql` (RLS). Keep the owner email as the placeholder in the file.
- Gear desk: `supabase/003_gear_desk.sql` (role 'gear', gear_feed pushed by `crew-sync.js` pushGear, gear_log append-only), page `public/gear.html`.
- Team Alignment sync: the board's Drive call (`claude.use('mcp')`) is bridged in `shim.js` to `/api/team-sheet`, which reads the sheet with a service account (`worker/google.js`, secret GOOGLE_SERVICE_ACCOUNT; the sheet must be shared with it as Viewer).
- Backups: `worker/backup.js` (cron 30 21 UTC, KV binding BACKUPS; owner-only /api/backups routes; Backups window in `public/crew-sync.js`).
- Gear not-available dates: `eq.off = [{ d, n?, why }]` on equipment; `offUnits` is subtracted in `unitsFreeFor`, so pickers, conflicts and the Gear desk all follow it.
- Tests: `node tests/gear-off.test.js <backup.json>`, `node tests/reminders.test.mjs`, `node tests/team-sheet.test.mjs`, `node tests/team-sync.test.js <backup.json> <sheet-base64.txt>` (XLSX_JS=local xlsx.full.min.js if offline), `node tests/backup.test.mjs <backup.json>`, `node tests/undo.test.js <backup.json>`, `node tests/load-backup.test.js <backup.json>`, SQL `tests/rls_crew_actions.sql` and `tests/rls_gear_desk.sql` (after `tests/pg_stub.sql`, both schema files) and `node tests/app.test.js <dir with events/, shooters/, gear/ JSON exports>` (Playwright, fake Supabase that mirrors the RLS rules). All checks must pass before pushing.
- Owner preference: he is fine with being told when an idea is weak; suggest better options.
- Look (locked 5 Nov 2026, Blush & gold): `public/app.css` (Open Sans, tokens, tiles, bottom bar) for sign-in, crew and gear pages; `public/board-theme.css` restyles the board in the app only (build-board.py inlines it right after the board's own styles, so the Claude-hosted board keeps its dark look) and styles the owner header/Home. Icons: `public/icons.js` (`MUTOS_ICON(name)`).
- Home screens: owner/manager Home is `public/home.js` on board.html (header `#mutos-bar`, Home `#mutos-home`, phone bottom bar, More sheet); `#board` in the URL shows the board, otherwise Home. Tiles click the board's own buttons by id. The board passes extra helpers in `MUTOS_APP.attach` (isShort, inboxCount, openRentals, goToDate…). Crew and gear pages have Home/Shoots/Days off and Home/Day/Out now/Items/Log tabs (`.bnav .tab[data-tab]`).
- Board tests open `board.html#board`; app.test.js clicks the Shoots/Day tabs before using those screens.
- Logins: roles owner, manager, crew, gear, staff (office employee), accountant (prepares salaries), kiosk (office screen). `mutosApp.homeFor(role)` in `app-core.js` picks each one's first page. App name and logo are just "Muto's".
- Clients: `supabase/004_studio.sql` (client_links, client_feed, client_itinerary) + `supabase/005_client_login.sql` (clients sign in with Gmail: `client_links.emails` lists up to 6 family Gmails; `client_list()` finds the signed-in Gmail's weddings; `client_get` / `client_save` only for listed Gmails, owner/manager get a read-only preview; nothing for anon). Page `public/client.html` (sign in first; `?k=<token>` picks a wedding when a Gmail has more than one); index.html sends a Gmail with no members row but a client link to it. Owner/manager window `public/clients.js` (MUTOS_CLIENTS: add client Gmails, WhatsApp "open …/client and sign in with …", Preview, see answers, Apply to board, add a new function as a shoot; keeps client_feed in step with the board). Home tile + "Needs you" card.
- Attendance & salary: same SQL (employees, att_settings, att_secret, att_punch via `att_punch()` which checks office location and the 6-digit office code server-side, att_requests with a trigger for advances ≤ one month's salary and fixes → punches, holidays, payroll_runs (accountant drafts, only the owner locks; locked never changes), payslips, att_log). Rules in `public/payroll.js` (MutosPay.monthCalc; decisions in project doc claude/attendance-and-salary.md). Pages: `work.html` (employee), `attendance.html` (owner + accountant), `office.html` (kiosk code screen). Shared loaders `att-data.js`.
- People + Work desk: `supabase/007_work_desk.sql` (006 = client phone sign-in, parked on branch `wip-phone-otp`). `people` (auto code M001…, Gmail, title, skills, crew_keys = the person's board shooter ids, several allowed), `people_private` (address, UPI, ID type + last 4 only; owner/accountant/self), `work_jobs` (one deliverable of a wedding; owner/manager assign; editors may only set editing/rendered + progress/drives/link; "changes" bumps round; final sets done_at), `work_reports` (daily, append-only, own same-day delete). Pages: `desk.html` (owner + manager: Jobs, Reports, Month, People; owner saving a Gmail with no login adds a `staff` member), `mywork.html` (editor: My jobs, Today's report, Me), shared `work-core.js` (MutosWork). Crew/work pages show a Jobs tab when the Gmail is on `people`; work.html sends people without an attendance row to mywork and opens the report after check-out. Dates of timestamps are compared in India time (`MutosWork.istDate`).
- Drive register: `supabase/008_drives.sql`. `drives` (holder = people id, empty = office; `holder` has no UPDATE grant and a trigger blocks it: only `drive_give` → `drive_answer` (receiver, or a keeper for returns to the office) or the owner's `drive_set_holder` change it, inside `mutos.quiet`), `drive_items` (what is on a drive; never deleted, `removed_at/removed_why`; `drive_move_item` copies or moves and keeps `moved_to`/`from_item`), `drive_moves` (one pending per drive), `drive_log` (append-only). Keepers = people with skill `data`. `people_directory()` gives names to everyone on `people`. UI `public/drives-ui.js` (MutosDrives.mount) in desk.html and mywork.html Drives tabs; `/api/notify-drive` pushes the receiver (their crew_keys' push_subs). The first import of the drive sheet is a separate SQL file given to Ravi (client names stay out of GitHub).
- Packages & payments: `supabase/009_bookings.sql` (packages; bookings per wedding_key with items = deliverables, plan = instalments, lock_on + grace_days; booking_payments append-only, owner deletes; `booking_summary()` = same sums as `money()` in clients.js; `client_get` returns `booking`, `client_save` refuses while locked and allows 1.5 MB for VIP photos). 009 redefines client_get/client_save from 005: when the phone sign-in branch (006) comes back, merge both. Clients window: Packages, "Package & payments" per wedding, WhatsApp payment reminder; Home "Payments overdue" / "Payments due". Work desk: "Add everything in the package".
- Client page extras: `answers.contacts` (people to call, `fn` = event id or '' for all) and `answers.vip` (name, relation, photo shrunk on the phone to a ~360px JPEG data URL). Crew see them per shoot through `crew_vip(event)` (009; checks the event is in the caller's crew_feed; finds the wedding via client_feed.functions). Sections use class `fn sec` (not counted as functions).
- Crew identity: one board name = one person (all their roles; days off block the name). `crew-sync.js` `groupCrew` also joins different names that share a Login Gmail (page key = first name, `keysFor(key)` = all names); team-updates mirrors days off to every name of the person. Test `node tests/crew-groups.test.js`.
- Shooter profile + bill (board): `openShooterProfile(key, back)` (Crew list "profile" button) and `openShooterBill(key, seasonId, back)` (also from Billing names); `personShoots(key, from, to)` uses each role's rate (full = rateFull or 2× short). The printable bill builds its page with '<' + 'html>' because build-board.py refuses a literal html tag in the board source.
- Sign-in page `index.html`: centred, page-level styles only (app.css untouched).
- Salary history before the app: `supabase/010_history.sql` (`salary_history` person × month, data as written in the salary sheet, never recalculated; payroll + self read, owner writes). Attendance → History tab; employee Pay tab "Before the app". The data import is a separate SQL file given to Ravi (salaries stay out of GitHub); it adds people not on the list as inactive.
- More tests: `node tests/payroll.test.js`, `node tests/crew-groups.test.js`, `node tests/studio.test.js <same data dir as app.test.js>` (also covers the work desk), SQL `tests/rls_studio.sql` (after the stub and schema, 002, 003, 004, 005) `tests/rls_work_desk.sql` (+ 007) `tests/rls_drives.sql` (+ 008) `tests/rls_bookings.sql` (+ 009) and `tests/rls_history.sql` (+ 010). A Cloudflare **Pages** project (`mutos-web`, output dir `public`, no build) serves the same pages, with one Hostinger CNAME `app` → the Pages address; `functions/api/[[path]].js` forwards /api/* to the Worker through the service binding `API` → `mutos-app`. The Worker keeps the crons and APIs and still answers on workers.dev.
